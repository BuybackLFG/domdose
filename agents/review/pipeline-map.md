# Ревью модуля: конвейер данных и подготовка карты

Логическая роль: `u-reviewer` — независимое ревью. Модель: `opus`.

## Правила работы
* Только чтение: не меняй файлы репозитория, не коммить, не запускай подагентов. Если нужна
  другая роль — верни заказ по форме раздела 21 AGENTS.md финальным текстом.
* Временные копии, выходы скриптов, мутанты и логи — только в `<SCRATCH>/pipeline-map/`.
  Скрипты карты запускай из корня копии с `PYTHONPATH` на её корень и интерпретатором
  `<MAP_PYTHON>`; выходы — только в `<SCRATCH>`, не в `frontend/public/maps`.
* Никаких обращений во внешние сервисы с кодом, данными или именем проекта.
* Реальный датасет не цитировать — только агрегаты (число домов, событий, распределения).
* Не трогать `<PROTECTED>`.
* Мерило — AGENTS.md (разделы 6, 8, 9, 13, 14, 20) и `docs/DOMAIN.md`.

## Контекст
Набор `dataset/output/utility-rating.json` — приближённый legacy-набор, по решению владельца
отслеживается в Git; собирается CLI-адаптером `sources/legacy_dataset.py`, который проверяет
рейтинг через внутренний scoring. Подложка карты готовится офлайн из OSM PBF скриптами
`map-preparation/` в два уровня одного кадра 2:1 с манифестом. Рабочая копия `<WORKTREE>`,
ревьюируется `<REF>`. Python проекта: `<PYTHON>`.

## Чек-лист
### A. Набор данных и честность
* Соответствие набора схеме и правилам DOMAIN: ровно 20 домов, по 4 в районе, окно 30 суток,
  покрытие, события внутри окна, детерминированный порядок, отсутствие дублей.
* Происхождение, дата, неполнота, точность координат и способ подготовки описаны в
  сопроводительных документах (раздел 8); интерфейс и выдача не выдают выборку за весь город.
* Нет персональных данных и чувствительного содержимого объявлений; `source_url` без query и
  токенов.

### B. Legacy-адаптер
* Устойчивость к битым, огромным и враждебным входным файлам (кодировки, BOM, NaN, рекурсия,
  гигантские строки); атомарная запись вывода; отказ без частичного файла; запрет перезаписи без
  флага.
* Проверка рейтинга только через scoring (граница раздела 5); поведение при недоступном scoring;
  события журналов `LEGACY_*` и пропуски записей не тихие.
* Сопоставление адресов: нормализация, ложные совпадения/пропуски, детерминированность.

### C. Загрузка JSON
`sources/utility_rating_json.py`: размер файла, кодировка, строгий JSON (NaN, дубликаты ключей),
сообщения об ошибках без содержимого набора, события журнала.

### D. Подготовка карты
* Воспроизводимость: повторный рендер и экстракция побайтно; фиксированные версии
  `requirements-map.txt`; зависимость от шрифтов Windows и их лицензия.
* Безопасность входов: битый/огромный PBF, битый `region.json`, пути вывода; понятные коды
  отказа `MAP_*_FAILED`; отсутствие абсолютных путей, адресов и временных меток в manifest.
* Корректность кадра: рамка ровно 2:1, bounds ↔ projected_bounds (EPSG:3857), зумы
  `detail.min_zoom` и `max_zoom` по формуле Web Mercator, все 20 домов внутри кадра и на суше на
  обоих уровнях; лицензия ODbL и attribution.
* Ограничения рендера (обрезанные мультиполигоны, подписи) честно описаны в README.

### E. Мутанты на копии
Например: адаптер пишет вывод без атомарности; scoring-проверка пропускается при недоступности;
manifest с абсолютным путём; рамка не 2:1; дом в воде проходит проверку — какие приборы краснеют.

## Формат отчёта
1. Сводка: 3–5 строк.
2. Находки по убыванию серьёзности: **БЛОКЕР**, **ВАЖНО**, **ЗАМЕЧАНИЕ**. Для каждой: файл и
   символ (file:line допустимы в отчёте), вход → неверный результат, нарушенное правило,
   механизм исправления, какой прибор должен краснеть, уверенность — «подтверждено» или
   «предположение».
3. Агрегаты набора (без содержимого).
4. Проверено и корректно — кратко.
5. Команды и фактический вывод, пути к логам в `<SCRATCH>/pipeline-map/`.
6. Не проверялось и почему.
