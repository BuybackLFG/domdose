# Ревью модуля: качество мерки, документация, мёртвый код

Логическая роль: `u-reviewer` — независимое ревью. Модель: `opus`.

## Правила работы
* Только чтение: не меняй файлы репозитория, не коммить, не запускай подагентов. Если нужна
  другая роль — верни заказ по форме раздела 21 AGENTS.md финальным текстом.
* Временные копии, мутанты и логи — только в `<SCRATCH>/tests-docs/`.
* Никаких обращений во внешние сервисы с кодом, данными или именем проекта.
* Не трогать `<PROTECTED>`.
* Мерило — AGENTS.md (разделы 11, 12, 13, 16, 20, 23) и `docs/DOMAIN.md`.

## Контекст
Мерка проекта — pytest-набор `tests/` (backend, контракты Compose и nginx, сторожа границ,
журналов, состава образов) и Vitest-набор `frontend/src/**/*.test.*`. Документы — `README.md`,
`AGENTS.md` (команды раздела 23), `docs/DOMAIN.md`, `dataset/*.md`, `map-preparation/README.md`,
`agents/**`, `TODO.md`. Рабочая копия `<WORKTREE>`, ревьюируется `<REF>`. Python: `<PYTHON>`;
frontend: `frontend/`.

## Чек-лист
### A. Годность мерки как системы
* Тесты, которые ничего не проверяют: assert на моке, проверка константы, тавтология, зелёные при
  удалении реализации. Найди их мутантами (удаление тела функции, возврат константы).
* Хрупкость: привязка к разметке и точным текстам там, где важен смысл; к порядку словарей; к
  времени, часовому поясу, локали, файловой системе Windows (CRLF, регистр путей); к сети.
* Изоляция: общий изменяемый state между тестами, глобальная настройка журналов, порядок
  запуска (`-p randomly` мысленно или реально, если доступно), параллельность.
* Скорость: самые медленные тесты (`--durations`), лишние дорогие проверки.
* Покрытие обязательного минимума раздела 12 по скорингу, API, frontend, архитектуре и
  конфигурации — составь матрицу «требование → тест», отметь пробелы.
* Помощники мерки (`tests/scoring_harness.py`, `tests/nginx_config.py`, `frontend/src/test/*`):
  не содержат ли собственной логики, повторяющей реализацию (тогда тест проверяет сам себя).

### B. Документация против факта
* Каждая команда в README, AGENTS.md (раздел 23), `map-preparation/README.md`,
  `dataset/LEGACY_ADAPTATION.md` — выполни или проверь по коду, что она верна (пути, флаги,
  порты, переменные окружения, имена сервисов).
* Утверждения о поведении (readiness, ворота данных, журналы, смена набора, лимиты) совпадают с
  кодом и конфигурацией.
* Раздел 13: в коде и долгоживущих документах нет координат `file:line`, чисел состояния без
  даты и команды, истории решений в комментариях; docstring ≤ 10 строк, русские.
* `TODO.md` отражает фактическое состояние ветки.

### C. Мёртвый код и дубли (раздел 20)
Неиспользуемые функции, классы, поля DTO, настройки и переменные окружения, файлы, экспортируемые
символы frontend, CSS-классы; дубли одной сущности в нескольких местах (каталог домов, порядок
категорий, формат ошибок). Для каждого кандидата — полная перепись потребителей по всему дереву
(backend, frontend, тесты, конфигурация, документация) с шаблонами поиска.

## Формат отчёта
1. Сводка: 3–5 строк.
2. Матрица «требование раздела 12 → тест» с пробелами.
3. Находки по убыванию серьёзности: **БЛОКЕР** (мерка зелёная при сломанном механизме, неверная
   инструкция запуска), **ВАЖНО**, **ЗАМЕЧАНИЕ**. Для каждой: файл и символ (file:line допустимы в
   отчёте), сценарий → последствие, нарушенное правило, механизм исправления, уверенность —
   «подтверждено» (мутант/команда и вывод) или «предположение».
4. Кандидаты в мёртвый код с доказательством отсутствия потребителей (область и шаблоны поиска).
5. Проверено и корректно — кратко.
6. Команды и фактический вывод, пути к логам в `<SCRATCH>/tests-docs/`.
7. Не проверялось и почему.
