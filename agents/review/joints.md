# Ревью модуля: стыки слоёв — сквозные контракты

Логическая роль: `u-reviewer` — независимое враждебное ревью. Модель: `opus`.

## Правила работы
* Только чтение: не меняй файлы репозитория, не коммить, не запускай подагентов. Если нужна
  другая роль — верни заказ по форме раздела 21 AGENTS.md финальным текстом.
* Временные копии, скрипты и логи — только в `<SCRATCH>/joints/`. Для сквозной эмпирики
  поднимай отдельный временный Compose-проект с уникальным именем и другим портом через
  override в `<SCRATCH>`; после — `down` и удаление только своих объектов. `<PROTECTED>` не трогать.
* Никаких обращений во внешние сервисы с кодом, данными или именем проекта.
* Мерило — AGENTS.md (разделы 1, 5, 6, 8, 12, 14, 25) и `docs/DOMAIN.md`.

## Контекст
Цепочка: браузер → `frontend` (Nginx, ворота данных) → `api` (FastAPI, `dossier`) →
`sources.scoring_client` → `scoring` (`api.scoring_main`) → `utility_rating`. Каждый слой
отдельно уже ревьюируется; здесь — только согласованность на границах: одно и то же понятие
должно означать одно и то же во всех слоях, а отказ одного слоя — честно доходить до
пользователя. Рабочая копия `<WORKTREE>`, ревьюируется `<REF>`. Python: `<PYTHON>`; frontend:
`frontend/`.

## Чек-лист
### A. Форма данных сквозь слои
Сравни поле за полем: `contract/utility_rating.py` ↔ `sources/scoring_protocol.py` ↔
`api/schemas.py` ↔ `frontend/src/features/dossier/types.ts` и валидаторы `api.ts`. Имена,
типы, nullable, единицы (оценки 0..1 против 0..100 в UI, часы, частоты), порядок категорий,
порядок событий (сортирует только backend), `weakest`, окно и часовой пояс (`+10:00` →
`Asia/Vladivostok` в UI), полуоткрытое окно и подпись периода. Поле, которое один слой
отдаёт, а другой молча игнорирует или додумывает, — находка.

### B. Коды и статусы ошибок end-to-end
Построй таблицу: исходная причина (нет файла, битая схема, неполный набор, scoring упал,
таймаут, редирект, 409, 500 scoring, `house_not_found`, неверный `house_id`, api не запущен) →
что пишет каждый слой в журнал (маркер, reason/code) → HTTP-статус и `error.code` api →
`X-DomDossier-Error` → поведение Nginx (ворота, `/api/` как есть, 502/504) → что видит
пользователь в UI. Ищи несовпадения, потерю причины, одинаковое отображение разных причин,
утечку деталей.

### C. Readiness и порядок старта
`scoring /ready` → `api /api/ready` (обе операции scoring) → ворота Nginx → `frontend /ready` и
`/health` → healthcheck и `depends_on` в `compose.yaml` → README. Проверь: смена набора и
`docker compose restart api`; пересоздание `api` с новым IP; падение `scoring` после того, как
снимок закэширован (api всё ещё готов? что видит пользователь?); холодный старт с битым набором.

### D. Данные и каталог карты
Адреса и `house_id` набора ↔ `PILOT_HOUSES` во frontend ↔ координаты и рамка manifest ↔
проверки `nginx /ready` и healthcheck ↔ скрипты `map-preparation`. Что происходит, если адрес в
наборе изменится на один символ (маркер пропадает — видно ли пользователю, ловит ли тест);
дублируется ли каталог домов в двух местах и кто источник правды.

### E. Конфигурация и имена
Переменные окружения: `core/config.py`, `core/logging.py` (allowlist), `compose.yaml`,
Dockerfile, README — совпадают ли имена, значения по умолчанию и описания; порты 8000/8001/80
во всех местах; пути журналов и volumes.

### F. Журналы сквозь сервисы
Можно ли по журналам трёх сервисов восстановить один пользовательский отказ (общий признак
запроса или хотя бы время и код); одинаковы ли правила секретов и формата.

### G. Мерка стыков
Какие сквозные свойства закреплены тестами (`tests/test_scoring_http.py`,
`tests/test_scoring_boundary_contract.py`, `tests/test_compose.py`, frontend-тесты), какие
только эмпирически, какие никак. Предложи минимальные сквозные сторожа.

## Формат отчёта
1. Сводка: 3–5 строк.
2. Таблица кодов ошибок end-to-end (раздел B).
3. Находки по убыванию серьёзности: **БЛОКЕР**, **ВАЖНО**, **ЗАМЕЧАНИЕ**. Для каждой: оба
   конца стыка (файл и символ, file:line допустимы в отчёте), сценарий → несогласованность и её
   последствие для пользователя, нарушенное правило, механизм исправления (один источник правды
   вместо синхронизации копий), какой прибор должен краснеть, уверенность.
4. Проверено и корректно — кратко.
5. Команды и фактический вывод, пути к логам в `<SCRATCH>/joints/`.
6. Не проверялось и почему.
