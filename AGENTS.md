## 1. Продукт, критичные потоки и смысл MVP
«ДомДосье» — сервис оценки надёжности покупки и аренды жилья во Владивостоке. Пользователь вводит адрес или ссылку на объявление и получает досье конкретного дома. Первый модуль — рейтинг коммунальной надёжности по истории отключений за скользящее окно 30 дней в сравнении с пилотной выборкой.

Критичные потоки MVP:

1. загрузить полный пилотный набор ровно из 20 домов и показать их на карте и в списке;
2. выбрать дом и получить его сводку, события, оценки категорий и худшую категорию;
3. вычислить рейтинг единым чистым расчётом, не смешивая отсутствие событий и отсутствие исходных данных;
4. честно показать границы приближённого набора и не выдавать выборку за весь город;
5. при ошибке источника или неполном наборе показать отказ данных, а не правдоподобный ноль.

**MVP не является разрешением отступать от инженерных правил.** Скоринг реализуется и проверяется особенно качественно; остальные сценарии делаются хорошо и пропорционально, без тяжёлого процесса ради процесса. Базовая архитектура, разведка, честные проверки, безопасность, отчётность, ветки и коммиты обязательны всегда. Требования логирования обязательны с момента введения соответствующего logging-пакета, назначенного ближайшим; остальные базовые правила этим не смягчаются.

Для документации, очевидной типографики и одноразового читающего исследования проверки пропорциональны риску. Для формулы, денег, живых данных, удаления и внешних побочных эффектов упрощений нет.

## 4. Корневая capability architecture
Карта ниже — обязательная структура после flatten, а не утверждение, что каждый файл уже существует. Пакеты создаются с реальным содержимым, без пустых обёрток «про запас».

```text
core/                    # конфигурация и единая сборка логирования
contract/                # общие доменные DTO, перечисления и ошибки
utility_rating/          # чистый расчёт коммунального рейтинга
dossier/                 # прикладной сценарий досье, сервисы и репозитории при необходимости
sources/                 # адаптеры файловых и внешних источников нормализованных данных
api/                     # FastAPI endpoints и HTTP-схемы
frontend/                # интерфейс после scaffolding
  src/components/        # только действительно межфичевые UI-примитивы
  src/features/          # страница, состояние, типы и проверки конкретной функции
  src/lib/               # единый API-клиент и общие утилиты
  src/test/              # общая настройка frontend-тестов
tests/                   # backend-тесты, сторожа и искусственные fixtures
docs/                    # предметные правила и журнал решений после его введения
agents/                  # реестр и определения логических ролей
requirements.txt         # прикладные зависимости
requirements-dev.txt     # зависимости разработки
README.md                # фактические команды, версии, запуск и структура
```

Python-пакеты размещаются **только в корне**. Общий `backend/`, вложенные пакеты-обёртки и дублирующий второй корень приложения запрещены. Слово backend обозначает только слой системы, а не разрешённый каталог. Не переносить структуру референса, если она противоречит этому правилу.

`core/logging.py` на момент этой редакции **отсутствует** и обязателен к введению ближайшим отдельным logging-пакетом до Compose. Это обязательство на будущее, а не утверждение о существующем файле. Требования к централизованным маркированным событиям становятся обязательными с момента введения logging-пакета; Compose не принимается без них. Настройки читаются централизованно; модули приложения не разбирают переменные окружения самостоятельно.

Если понадобится постоянное хранилище, конкретный репозиторий располагается внутри `dossier` как отдельный модуль доступа к данным. Новый корневой пакет для него не создаётся. API не выполняет SQL и не знает детали драйвера.

## 5. Архитектурные границы и паттерны
### Фактическое состояние utility-rating до Compose
На момент этой редакции internal HTTP scoring и `api.scoring_main` **не существуют**. Существующие `dossier/service.py` и `sources/legacy_dataset.py` вызывают `score_city` напрямую. Это явно названное переходное состояние текущего модуля, а не утверждение, что внутренний сервис уже реализован.

```text
core                 -> никаких прикладных зон
contract             -> никаких прикладных зон
utility_rating       -> contract
sources              -> contract, core, utility_rating  # существующий прямой вызов legacy_dataset
dossier              -> contract, core, sources, utility_rating  # существующий прямой вызов service
api.main             -> contract, core, dossier
tests                -> проверяет зоны, но не является их производственной зависимостью
```

Существующие прямые вызовы не являются второй формулой и не делают текущий utility-rating непринятым задним числом. До Compose нельзя добавлять новые прямые потребители расчёта вместо подготовки целевой границы. В `utility_rating` по-прежнему запрещены FastAPI, SQL, сеть, файлы, системные часы и случайность.

### Обязательная цель Compose
Compose-пакет обязан заменить оба существующих прямых вызова на внутренний HTTP через адаптер `sources` и ввести `api.scoring_main`; это неустранимое условие его приёмки.

```text
core                 -> никаких прикладных зон
contract             -> никаких прикладных зон
utility_rating       -> contract
sources              -> contract, core
dossier              -> contract, core, sources
api.main             -> contract, core, dossier
api.scoring_main     -> contract, core, sources, utility_rating
tests                -> проверяет зоны, но не является их производственной зависимостью
```

После перехода `api.main` и `dossier` не импортируют формулу, а только HTTP-дверь `api.scoring_main` связывает сервис с чистым расчётом. Обратных и поперечных скрытых зависимостей нет; и текущие, и целевые границы проверяются относящимися к этапу сторожами.
* **KISS/YAGNI.** Если сценарий ясно закрывается функцией, пишется функция, а не иерархия классов.
* **DTO.** На HTTP и конфигурационной границе используется Pydantic. Внутри — небольшие неизменяемые dataclass и Enum. Не создавать три одинаковые модели без несовместимости слоёв.
* **Service layer.** `dossier` объединяет источник и расчёт в понятный сценарий и возвращает результат либо явное состояние отсутствия данных.
* **Adapter.** В целевой границе специфика файлового набора, scoring HTTP и любого согласованного self-host сервиса скрыта в `sources`; домен не зависит от транспорта и чужого формата ответа.
* **Repository.** База изолируется конкретными методами вроде `get_by_id` и `save`. Generic-репозиторий без нескольких реальных потребителей запрещён.
* **Strategy.** Допускается только при реальном динамическом выборе алгоритма, а не ради схемы.
* Новая абстракция появляется вместе с проверкой её границы. Два одинаковых пути данных хуже одного простого.

Сейчас `utility_rating` получает нормализованные события и полную выборку от существующих прямых вызывающих; после Compose — от internal scoring-сервиса. Формула в обоих состояниях живёт только в `utility_rating` и не дублируется в `api`, `dossier`, `sources`, SQL, JSON или TypeScript. Frontend не обращается к scoring напрямую.

## 6. Интерфейс MVP, offline-карта и географические сервисы
Основной экран строится сверху вниз:

1. **Карта Leaflet сверху.** При полном пилотном наборе на ней ровно 20 голубых точек.
2. **Сводка выбранного дома.** Адрес, район, состояние данных и общий рейтинг, если он доступен.
3. **События дома.** Категория, начало, окончание или продолжающийся статус и доступные признаки.
4. **Категории.** Четыре оценки с понятным состоянием недоступных данных.
5. **Худшая категория (`weakest`).** Она выделяется и связывается с ограничением общего рейтинга, не выдаваясь за ещё одну независимую оценку.
6. **Список адресов.** Все дома пилотной выборки; выбор из списка и карты меняет одно состояние.

### Обязательный offline-контракт
Offline означает отсутствие обращений к внешнему интернету для карты и географических функций. **Внешние online OSM tiles и любые внешние online tile URL запрещены.** Нельзя добавлять их как основной источник, скрытый fallback, резерв при ошибке локального asset или режим разработки.

Runtime-запросы к внешним online экземплярам Nominatim, Photon, Valhalla и другим геосервисам запрещены. Online fallback не предлагается и не реализуется. Self-host на своей машине разрешён: запрос к явно локальному сервису не считается внешним интернетом, но нуждается в конкретном сценарии и не должен быть overkill. Запрет внешних сервисов не является запретом всех self-host вызовов.

Базовый MVP использует только:
* Leaflet с локальным `L.imageOverlay` и заранее подготовленным изображением карты Приморского края; его географические bounds покрывают все 20 домов и имеют проверяемое преобразование координат в положение markers;
* локальные markers, icons, CSS, изображение и прочие assets, поставляемые вместе с frontend;
* локальный поиск и фильтрацию по каталогу тех же 20 адресов, без обращения к геокодеру;
* заранее известные координаты из пилотного набора, а не вычисленные браузером через сеть.

Подготовка изображения карты — отдельный согласованный этап, а не runtime-обязанность приложения. Этап фиксирует источник, лицензию и attribution, bbox, размеры, ограничения проекции и команду воспроизведения. Готовый локальный asset затем используется приложением без скачивания карты.

Полноценный self-host tile server сейчас не требуется. Он допускается позднее отдельным решением, только если действительно понадобится slippy map с масштабами и tiles. Наличие Docker или референса не является такой необходимостью.

Valhalla предназначена исключительно для маршрутизации, если отдельный сценарий её оправдает. Valhalla не является tile server и не даёт подложку Leaflet; для отображения 20 домов она не нужна. Self-host Nominatim или Photon допустим позже только для доказанной потребности в геокодинге; в базовый локальный поиск по каталогу они не добавляются.

Координаты не выдумываются. Неполный набор или отсутствие координат показывается как дефект данных, а не имитация 20 точек. Приближённые legacy-координаты маркируются ограничением набора.

Frontend использует один API-клиент, относительный `/api` и одинаковые адреса в dev и production. CORS не служит обходом несогласованных конфигураций. Запросы поддерживают отмену; loading, empty, error, «нет событий» и «нет исходных данных» разделены. Карта, поиск, список и сводка не показывают разные выбранные дома.

## 7. Скоринг как критичный контур
Перед правкой расчёта обязательно прочитать `docs/DOMAIN.md`. Его предметные правила не заменяются примером, прежней реализацией или соображениями удобства.

Ключевые инварианты:
* четыре категории: горячая вода, холодная вода, электричество и отопление;
* только скользящее окно 30 дней с границами и часовым поясом из `docs/DOMAIN.md`;
* аварийное событие имеет базовый вес `1,0`, плановое — `0,4`;
* массовое или стихийное событие дополнительно умножается на `0,5` ровно один раз, даже при сочетании обоих признаков;
* метрики — взвешенная частота, взвешенные часы и максимальная взвешенная длительность события;
* пилотная выборка содержит ровно 20 домов: по 4 в Ленинском, Первомайском, Первореченском, Советском и Фрунзенском районах;
* оцениваемый дом входит в выборку ровно один раз; дома без событий остаются в знаменателе;
* среднее — сумма значений по этим 20 домам, делённая на 20, а не среднее города и не среднее только домов с отключениями;
* при метрике не выше среднего штраф равен нулю;
* после превышения штраф равен `min(1, log2(ratio)/3)`;
* веса метрик — `0,4 / 0,4 / 0,2`;
* веса категорий — электричество `0,30`, холодная вода `0,25`, отопление `0,25`, горячая вода `0,20`;
* общий рейтинг не выше `худшая_категория + 0,25`;
* значения конечны, длительности и счётчики неотрицательны, рейтинги ограничены `[0, 1]`;
* нулевое среднее корректной неотрицательной выборки не приводит к делению на ноль;
* пустой или неполный набор из 20 домов означает «нет данных», а не нулевое среднее;
* для численного общего рейтинга нужны исходные данные всех четырёх категорий по полному набору;
* недоступная категория не заменяется `1,0`, веса остальных не перенормируются;
* отсутствие событий при доступном источнике и отсутствие исходных данных — разные состояния.

Изменение формулы, весов, окна, районного состава или знаменателя — содержательное изменение контракта. Оно требует прямого решения владельца, обновления `docs/DOMAIN.md`, независимой мерки и отдельного ревью. Его нельзя называть рефакторингом.

Результат описывает только выбранные 20 домов. Ни API, ни интерфейс, ни отчёт не вправе называть его средним или рейтингом всего Владивостока.

## 8. Данные и приближённый legacy dataset
Для MVP допустим приближённый legacy dataset. Его использование не ослабляет требования к полной выборке и формуле. Происхождение, дата, неполнота, точность координат, возможные расхождения с реальной историей и способ подготовки фиксируются в сопроводительном описании набора.

Интерфейс и выдача обязаны честно маркировать приближённый характер данных. Нельзя скрывать ограничения мелким техническим примечанием, которое противоречит основному тексту результата. Неизвестные события не дополняются выдуманными; отсутствие сведений не становится нулём.

`dataset/` не игнорируется целиком: схемы и документация `schema`, `README`, `COLLECTION_PROMPT`, `LEGACY_ADAPTATION`, а также `docs/schema/` законно отслеживаются в Git. Вне Git находятся только реальные JSON-выгрузки и промежуточные данные в `dataset/`, а также `output/`; `.gitignore` разделяет эти данные и отслеживаемые файлы точечно. Реальные данные не вставляются в тесты, prompt, внешние запросы, отчёты и коммиты без конкретного разрешения владельца.

Тестовые fixtures обязаны быть явно искусственными и минимальными. Демонстрационные значения нельзя выдавать за реальную историю дома. Сбор новых реальных объявлений, отключений и персональных данных — отдельный согласованный этап, а не побочный эффект разработки интерфейса.

## 9. Фундаментальность правки
**Правка чинит механизм, а не наблюдение.** Заплатка под конкретный адрес, дом, событие, район, пример API, имя файла или координату запрещена.
* Условие приёмки формулируется правилом поведения: что система делает и чего не делает при проверяемом признаке входа независимо от конкретного образца.
* Ветвление опирается на свойство данных, а не на происхождение или идентификатор примера. Если различие действительно предметное, оно должно быть выражено проверяемым полем и правилом.
* Литерал ожидаемого ответа, обход валидации, специальный случай для теста и ослабленная проверка не принимаются даже при зелёном наборе.
* Проверка охватывает население шире исходного примера: сколько входов затронуто, скольким правка помогает, скольким может навредить и какие входы остаются вне охвата.
* Частное решение допустимо только явно названным: что закрывает, чего не закрывает, цену бездействия и способ снятия ограничения. После введения памяти оно фиксируется как технический долг; до её введения — в отчёте и заказе на будущую запись.
* Нельзя изменять предметный контракт только потому, что существующий прибор обнаружил неудобный результат. Сначала доказывается, что неверен контракт, а не прибор или вход.

## 10. Полная разведка до изменения
До правки исполнитель получает ответы инструментами, а не по памяти:

1. **Существующее.** Поиск по имени, синонимам и смыслу действия; похожая реализация под другим именем тоже считается найденной.
2. **Потребители.** Полная перепись вызовов, импортов, чтений полей, API-клиентов, схем, конфигурации, переменных окружения, тестов, команд и документации.
3. **Последствия.** Для каждого потребителя описано, что изменится на обычном, граничном и отказном входе; проверены значения по умолчанию и порядок вызовов.
4. **Долг.** Названы второй путь данных, второй дефолт, дублирование сущности, временная совместимость и цена их сохранения.

Разведка включает сигнатуры, DTO, ошибки, тесты, обработчики отказов, frontend-потребителей и фактические команды запуска. Формулировка «примерно работает так» означает, что разведка не закончена.

Незнакомые или чужие изменения сначала исследуются как работа пользователя. Их нельзя удалять, перезаписывать или «чистить» ради удобного диффа. Найденное противоречие возвращается заказчику с точными символами и последствиями.

## 11. Условие приёмки и мерка до работы
До содержательной правки называются наблюдаемый результат, минимально достаточная проверка, население измерения и критерий неуспеха. «Стало лучше» без способа измерить ухудшение не является меркой.
* Для дефекта сначала создаётся проверка, которая **падает на исходном поведении**, затем исправление. Первый запуск после исправления ничего не доказывает без воспроизведения красного.
* Независимый `u-tester` пишет прибор и эталоны, отдельный `u-executor` пишет реализацию. Один агент не создаёт обе стороны для скоринга и нетривиального исправления.
* Население, знаменатель, допустимые входы и условия годности замера объявляются до прогона. После увиденного результата их нельзя менять ради желаемой доли.
* Прибор обязан уметь показать ухудшение и обнаруживать подделку механизма, а не только отсутствие конкретной правки.
* Запрещены подгонка ожидания под фактический вывод, удаление неудобного теста, ослабление assert, смена фикстуры без предметной причины и перевод красного в «ожидаемый» без класса отказа.
* Изменение мерки и изменение предмета выполняются раздельно и отдельными коммитами, когда прибор и реализация входят в Git. Сначала независимый прибор с доказанным красным, затем реализация.
* Если прибор изменился после правки, это называется проверкой задним числом. Нужно показать, на каком исходном или мутантном варианте он краснеет, и не выдавать его за соблюдение порядка.
* Если измерить нельзя, работа явно маркируется непроверенной. «Непроверяемо» никогда не превращается в «зелёно» или «в порядке».

Для небольшой новой функции красный тест может фиксировать отсутствие требуемого поведения. Для документации и очевидной типографики достаточно чтения диффа и поисковых проверок; искусственный падающий тест не требуется.

## 12. Тесты, регрессия и пропорциональные проверки
### Обязательный минимум скоринга
Независимые табличные и граничные сцены покрывают:
* отсутствие событий при доступных данных и нулевое среднее;
* дом равен среднему и лучше среднего — штраф `0`;
* превышения `2×`, `4×`, `8×` и больше;
* аварийное и плановое события, массовый и стихийный признаки, их сочетание без двойного `0,5`;
* участие домов без событий в знаменателе всех 20 домов;
* ровно по 4 дома в каждом из пяти районов и единственное вхождение оцениваемого дома;
* все три метрики, включая взвешивание длительности до вычисления максимума;
* веса категорий и ограничение общего рейтинга худшей категорией;
* границы окна, продолжающееся событие, клиппирование длительности и мгновенное событие;
* пустой и неполный набор, недоступную категорию и запрет перенормировки;
* отрицательные, NaN, бесконечные и структурно неверные входы;
* противоречивую пару положительной метрики дома и нулевого среднего полного набора;
* один полный независимо посчитанный сценарий с численным эталоном, не полученным вызовом той же функции.

Для нового дефекта скоринга сначала воспроизводится падающий тест. Mutation-тестирование и исчерпывающий property-based набор по умолчанию не требуются, но отдельные мутанты допустимы для проверки годности критичного сторожа.

### Остальное приложение
* API: happy path, валидация, дом не найден, нет данных и недоступность зависимости, если применимо.
* Frontend: основной сценарий выбора дома, loading, empty, error, отсутствие исходных данных, отмена устаревшего запроса, TypeScript и линт по фактическим scripts.
* Визуальная проверка основного экрана через Browser skill после появления интерфейса: карта, голубые точки полного набора, список, сводка, категории и weakest.
* Архитектура: сторож запрещённых зависимостей чистого скоринга и обратных импортов корневых зон.
* Конфигурация: проверка безопасных значений, отказ неполного обязательного окружения и отсутствие секретов в снимках.

### Честность результата
Свой красный нельзя скрывать. Нужно назвать упавшую сцену, текст причины и отличить её от baseline прогоном на чистом `HEAD` или отдельной копии без чужих незакоммиченных изменений. Для этого не применяются разрушающие команды и не удаляются чужие правки.

Итоговая сдача с новым красным запрещена. Если красный уже существовал и не относится к задаче, он фиксируется отдельно с доказательством baseline; его наличие нельзя замалчивать.

Каждая проверка описывается командой, населением и фактическим выводом. Незапущенное не называется пройденным, доля без знаменателя не называется результатом, число пройденных тестов без лога не называется подтверждением.

## 13. Кодстайл, комментарии и долгоживущие документы
* Docstring и комментарии — русские, краткие и технические. Имена символов, ключи JSON, поля БД, маркеры логов, коды причин и имена событий — английские.
* Docstring функции, класса или метода занимает не более **10 строк исходника**, включая кавычки. Он описывает назначение, параметры, результат и исключения без истории и рассуждений.
* Комментарий объясняет только неочевидный технический контракт. План, процесс, дата, номер задачи, имя исполнителя, состояние тестов и история решения в коде не живут.
* Docstring теста может называть класс отказа, который он ловит, но не писать «сейчас красный», «на сегодняшнем дереве» или «теперь работает».
* Ссылки на код внутри docstring даются символом модуля, класса или функции. Координаты `file:line` в коде и долгоживущих документах запрещены: они допустимы только в одноразовом отчёте, разведке и переписке.
* Числа состояния и истории — счёт тестов, число файлов, текущие расходы, длительность прогона, размер покрытия — не вписываются в код и долгоживущие документы. Исключение памяти описано в разделе 18: число всегда сопровождается датой и командой повторного снятия.
* Предметные константы формулы не считаются «числами состояния»; они живут в одном месте расчёта и объясняются `docs/DOMAIN.md`.
* Python использует только абсолютные импорты от корня. Frontend сохраняет принятые относительные импорты и фактические соглашения scaffolding.
* `README.md` содержит протухающие пути, версии, порты, команды и состояние окружения. Не оставлять в нём заведомо неверные инструкции; перед изменением команды обновить документацию тем же рабочим пакетом.

## 14. Обязательное централизованное логирование
Требования этого раздела обязательны **с момента введения отдельного logging-пакета**. После введения `core/logging.py` становится единственной точкой сборки логгеров и handlers для Python. Создавать в Python-модулях самостоятельные file handlers, менять глобальную конфигурацию или использовать `print` вместо события запрещено. До пакета нельзя утверждать, что централизованные маркированные события и файловый `execution.log` уже реализованы. Файловый журнал Nginx настраивается в Compose отдельно по разделу 25 без центрального log-сервера.

Формат ориентирован на чтение человеком и машинный поиск:

```text
[TIMESTAMP] [LEVEL] [MODULE] [MARKER] message | data={...}
```
* Каждое значимое событие имеет короткий английский `[MARKER]`; перед заведением нового ищется подходящий существующий.
* Сообщение кратко называет произошедшее и исход. Метаданные содержат только заранее нужные поля: идентификатор операции, код причины, счётчики и безопасный адрес входа.
* Отказ, исключение, пропуск, недоступность источника, отбрасывание значения и выбор особой ветви не остаются тихими. Их события позволяют ответить, что и сколько было потеряно.
* Для изменения критичного поведения ожидаемые маркеры и поля объявляются в мерке до реализации; проверка ловит их машинно, а не глазами.
* Файловый `execution.log` пишется file handler. Консольный захват не подменяет его: переносы и потери консоли делают такой журнал непригодным для точного разбора.
* Секреты, ключи, пароли, строки подключения, токены, персональные данные и чувствительное содержимое объявлений не логируются. Ошибка внешнего сервиса очищается от query с секретом.

Лог — дополнение к тесту, а не его замена. Чистый скоринг остаётся без файлового ввода-вывода; события формируются на прикладной границе `dossier`, `sources` или `api`.

## 15. Артефакты запусков
Каждый рабочий, интеграционный или проверочный запуск, результат которого используется для приёмки, диагностики или отчёта, получает каталог:

```text
.artifacts/runs/YYYYMMDD_HHMMSS/
```

Полный обязательный состав действует с момента введения logging-пакета. До него отсутствие `execution.log` обозначается `NOT_IMPLEMENTED`, а не подменяется консольным выводом или выдуманным файлом; для Compose полный состав обязателен без исключений:
* `execution.log` — журнал из централизованного file handler, включая маркированные события и фактический отказ; для Compose сохраняются отдельные `execution.log` каждого сервиса по разделу 25 без их объединения в центральный журнал; если приложение не запускалось, причина прямо указана в `REPORT.md`;
* `env_snapshot.json` — фактическая конфигурация и окружение с удалёнными секретами и персональными данными; используется allowlist безопасных имён, а не надежда на ручную чистку;
* `test_results.log` — команды и фактический объединённый вывод проверок; при незапущенной проверке записывается `NOT_RUN` и причина, а не выдуманный успех;
* `REPORT.md` — человеко-читаемый отчёт по разделу 16;
* `db_dump.json` или `db_dump.sql` — **только если в этом запуске действительно использовалась тестовая или локальная БД**, с указанием её изолированного назначения.

Если БД не использовалась, дамп не создаётся и это не считается недостающим артефактом. Дамп живой базы, живого тома и несанкционированное снятие журнала рабочей службы запрещены. Штатные файлы локального Compose собираются только по разделу 25. Для разбора другого живого отказа владелец передаёт отдельные безопасные строки; агент не обходит запрет прямым подключением.

`.artifacts/` находится вне Git. Каталоги прогонов, реальные JSON-выгрузки и промежуточные данные в `dataset/`, содержимое `output/`, `.env`, `.venv` и `node_modules` не коммитятся. Отслеживаемые схемы и документация dataset сохраняются в Git по разделу 8. Ссылка на прогон в отчёте не превращает его в публичный источник чувствительных данных.

## 16. Отчёты Before/After и завершение работы
Отчёт о содержательной правке пишется для человека, который не открывал код. Название функции без объяснения её поведения не считается описанием результата.

Обязательная структура:

1. **Задача и условие приёмки.** Какое правило поведения требовалось и какая мерка была объявлена до работы.
2. **Реальный вход.** Воспроизводящий пример и его минимальный фрагмент: структура события, запрос или безопасная искусственная fixture. Нельзя заменять находку абстрактным «пришли данные».
3. **Before.** Что происходило до правки, чем это нарушало контракт и какой механизм вызывал результат; для кода показывается короткий фрагмент до.
4. **After.** Фрагмент после и точечное объяснение, как изменился механизм, а не только результат одного примера.
5. **Население и замер.** Что проверялось, знаменатель, классы входов, что осталось вне охвата, числа до/after при наличии и доказательство красного исходного прибора.
6. **Команды и фактический вывод.** Полные команды, вердикт каждой, ключевые строки вывода и путь к каталогу прогона. Не приписывать команде результат, которого в выводе нет.
7. **Логи.** Маркеры и безопасные строки до/after для поведения, где лог является прибором.
8. **Изменённые файлы и коммиты.** Назначение каждого файла; отдельно названы коммиты прибора и реализации, если они требовались.
9. **Риски и долг.** Что ухудшилось, какие допущения приняты, что не проверялось, цена долга и следующий шаг.

Чувствительный реальный вход не публикуется. В таком случае показывается минимальная обезличенная форма с явной пометкой об обезличивании; нельзя называть её дословной реальной выгрузкой.

Полный отчёт сохраняется в `REPORT.md` каталога прогона, а содержательное резюме возвращается пользователю. Для мелкой документационной правки достаточно краткого списка изменений и фактически выполненных поисковых проверок, без искусственно раздутого протокола.

## 17. Платные API, живые данные и секреты
Платный вызов, отправка данных наружу, запись в живую БД, удалённая инфраструктура и необратимая операция требуют явного разрешения владельца **на конкретную операцию и команду**. Разрешение на один запуск не распространяется на следующий.

До платного прогона называются провайдер, модель или сервис, назначение, ожидаемая цена, население, лимит расхода и критерий остановки. Дверь к живому ключу — `u-ops`; остальные роли готовят команду, но не запускают оплату самостоятельно.

Если провайдер поддерживает учёт по конкретному ключу:

1. до вызовов снимается pre-balance именно используемого ключа;
2. после вызовов снимается post-balance того же ключа;
3. в журнал и отчёт записывается `[BALANCE] Pre: ... | Post: ... | Spent: ...` с полной доступной точностью, без округления малой траты до нуля;
4. стоимость и токены каждого вызова фиксируются отдельно, если провайдер их предоставляет; транспортный отказ отделяется от оплаченного ответа.

Общий баланс аккаунта не подменяет показание ключа. Недоступный счётчик записывается как `unknown` с причиной, а не как ноль. Расхождение внутреннего учёта и счётчика называется числом.

Секреты не попадают в Git, отчёты, логи, prompt, поисковые запросы и внешние payload вне разрешённого назначения. `.env` игнорируется; `.env.example` содержит только имена и безопасные примеры. Скомпрометированный секрет не «заметает» удалением строки: владельцу сообщается о нужде отзыва ключа.

## 18. Оперативная память: обязательное будущее введение
`CONTEXT_RAG.md` в корне и сторожа его структуры **обязаны быть введены ближайшим отдельным пакетом памяти после уже назначенного Compose-пакета**, если владелец не задаст иной порядок. Это правило на будущее, а не утверждение, что файл уже существует. Не создавать его вскользь внутри независимой задачи и не ссылаться на записи, наличие которых не проверено.

Пакет введения назначает форму, владельца записи, минимальные проверки и способ разрешения конфликтов веток. После введения память становится единственным местом оперативного состояния, технического долга и машинно исполняемых инвариантов; параллельные файлы памяти запрещены.

Обязательная структура памяти:

1. **Текущее состояние и стек.** Краткая карта реальных модулей и их связей без выдуманного статуса.
2. **Recent Changes.** Не более десяти последних содержательных итераций; вытесненные записи переносятся в архив без переписывания истории.
3. **Tech Debt и ограничения.** Механизм долга, затронутое население, цена бездействия и условие снятия. Фраза «потом улучшить» без цены не считается записью долга.
4. **Invariants.** Правила автоматических правок; у каждого назван конкретный сторож — тест или проверяемая сцена, которая краснеет при нарушении. Инвариант без сторожа считается незакрытым долгом, а не надёжной гарантией.
5. **Snapshots и архив.** Только нужные исторические показания в полном формате ниже.

Снимок допускается только тремя частями одновременно: **число, дата и команда**, которой его можно снять заново. Без команды число не записывается. Устаревший снимок не переписывается задним числом: рядом добавляется новый с датой, старый сохраняет исходный контекст.

Писатель памяти после её введения — `u-executor`. Он вносит готовую формулировку после успешной итерации и проверок тем же коммитом, если это не меняет границу замера. Любая роль может найти долг или инвариант, но возвращает заказ `u-executor` с готовой строкой, а не правит память сама.

Если запись памяти меняет прибор или его население, она оформляется отдельно до прогона. При многоэтапной работе через ревью главный агент назначает одну согласованную партию записи до начала следующей волны. Нельзя оставлять строки, которые код уже сделал ложными.

До отдельного пакета введения найденные долги и инварианты фиксируются в итоговом отчёте и в заказе на этот пакет. Такое временное состояние не называется полноценно введённой памятью.

## 19. Журнал решений и преемственность OpenCode
`docs/DECISIONS.md` **обязателен к введению тем же отдельным пакетом памяти после Compose** либо заранее назначенной частью этого пакета. Это также не утверждение о его нынешнем наличии.

После введения журнал хранит только решения, которые дороже переоткрыть, чем записать: выбор между жизнеспособными вариантами, отказ от очевидного пути и неочевидную границу. Он не дублирует каждый коммит и не превращается в протокол встреч.

Каждая запись содержит:
* устойчивый идентификатор и дату;
* контекст, который заставил принимать решение;
* принятое решение;
* отвергнутые альтернативы и причину отказа от каждой;
* следствия, ограничения и связь с инвариантом или правилом, если решение обязательно к исполнению.

Журнал только дополняется. Идентификаторы не переиспользуются. Отмена оформляется новой записью, а в старой меняется только ссылка на отменившую. Само объяснение решения не заменяет сторож в коде.

Устойчивые предметные правила остаются в `docs/DOMAIN.md`, инженерные — здесь, оперативное состояние — в памяти после её введения, причины архитектурного выбора — в журнале решений. Один факт не копируется во все хранилища.

Ручной `SESSION_HANDOVER` **не требуется и не вводится**. Текущая преемственность обеспечивается механизмами OpenCode session/journal: главный агент сохраняет самостоятельные задания, результаты, идентификаторы детей и незавершённые заказы в доступной сессии. Не создавать дополнительный файл сдачи и не выдавать журнал сессии за замену обязательной памяти или отчёта прогона.

## 20. Мёртвый код и перепись после крупного пакета
Неиспользуемые функции, импорты, поля, настройки, закомментированные реализации и заглушки «на будущее» удаляются, когда доказано отсутствие потребителей. Настройка, которую ничто не читает, тоже мертва и удаляется вместе с безопасным примером окружения.

Перед удалением выполняется полная перепись по всему дереву: backend, frontend, тесты, приборы, миграции, конфигурация запуска, документация, команды и имена переменных. Учитываются динамические точки входа и внешние вызовы API. «Поиск ничего не нашёл» допустим только с описанием области и шаблонов поиска.

После удаления запускаются относящиеся проверки и регрессионный набор. Форма, которая уже имеет читателя и ждёт согласованного производителя, не объявляется мёртвой лишь из-за временного отсутствия данных: её состояние и владелец следующего шага называются явно.

Крупный пакет, новый корневой capability или новая схема не закрываются без переписи:
* каждая новая сущность имеет определение, отличие от соседних и реального читателя;
* дубли одной сущности сводятся к одной форме либо получают проверяемое основание различия;
* отсутствующая доменная форма не остаётся случайным словарём или кортежем;
* всё дерево сверяется с зависимостями, кодстайлом, логированием, секретами и этим регламентом;
* каждая находка исправляется либо получает цену долга и следующий шаг.

Перепись ведут `u-architect` и `u-explorer`, независимую сверку — `u-reviewer`. Она не должна превращаться в массовый посторонний рефакторинг внутри коммита функциональной правки.

## 21. Работа через агентов, роли и модели
**С этого момента написание содержательных правок поручается агентам, а не главной сессии в одиночку.** Главная сессия владеет задачей, запускает один уровень детей, передаёт контракты, сводит результаты и отвечает владельцу. Самостоятельно она может ответить по уже прочитанному, исправить очевидную опечатку или выполнить явно названную владельцем команду без обхода правил.

Полный реестр и определения — `agents/README.md` и соседние файлы. Наличие Markdown-определения не доказывает регистрацию нативного пресета: вызов идёт через фактически доступный `subagent` типа `explore` для чтения или `general` для записи, а логическая роль указывается в самостоятельном prompt.

| Роль | Основная ответственность | Модель и стартовый reasoning |
|---|---|---|
| `u-architect` | границы, контракты и декомпозиция нескольких зон | `k3.1-pro`, `max` |
| `u-explorer` | широкая перепись кода, потребителей и конфигурации | `k3.1-pro`, `low` |
| `u-planner` | самостоятельный план и риски одной нетривиальной правки | `k3.1-pro`, `high` |
| `u-tester` | независимая мерка, красный тест и строгий контур скоринга | `k3.1-pro`, `high` |
| `u-executor` | минимальная реализация готового плана и отчёт | `kimi-for-coding`, `high` |
| `u-reviewer` | независимое ревью механизма, рисков и доказательств | `k3.1-pro`, `high` |
| `u-ops` | среда, сборка, прогоны, артефакты и согласованные операции | `kimi-for-coding`, `low` |
| `u-frontend` | интерфейс и его основные и визуальные проверки | `kimi-for-coding`, `high` |
| `u-golden` | независимые эталоны и мерила, особенно скоринга | `k3.1-pro`, `high` |
| `u-analyst` | причинный разбор потерь и аномалий без правок | `k3.1-pro`, `high` |
| `u-refactor` | поведенчески нейтральная гигиена кода | `kimi-for-coding`, `low` |
| `u-agentsmith` | роли, модели, полномочия и передачи | `k3.1-pro`, `high` |
| `u-lawsmith` | гигиена регламента без самовольной смены смысла | `k3.1-pro`, `low` |
| `u-prompt` | черновики prompt и схем с независимой приёмкой | `k3.1-pro`, `high` |
| `u-researcher` | согласованные внешние источники и технические гипотезы | `k3.1-pro`, `high` |

Полные provider ID указаны в `agents/README.md`: интеллектуальные роли используют `kimi-code-plan-global/k3.1-pro`, исполнители — `kimi-code-plan-global/kimi-for-coding`. Не выдумывать идентификаторы. Reasoning выбирается по сложности: `low` для механического, `high` по умолчанию, `max` для архитектуры, скоринга и рискованного анализа; `none` допустим только для детерминированного простого действия на `kimi-for-coding`.

Базовый маршрут содержательной работы:

```text
u-architect -> u-explorer / u-planner -> u-tester -> u-executor -> u-reviewer -> u-ops
```
* Для одной небольшой зоны `u-architect` можно не вызывать, но пропуск и причина называются; разведка, независимая мерка и ревью не исчезают из-за сокращения маршрута.
* `u-frontend` заменяет или дополняет исполнителя в своей зоне, не получая права менять формулу.
* `u-golden` привлекается для независимого численного эталона скоринга и не копирует ответ из реализации.
* Независимые исследования запускаются параллельно; пишущие дети получают непересекающиеся зоны. Нельзя дублировать работу активного ребёнка или оставлять его результат без сбора.

Подагент не запускает подагента: глубина — один уровень детей главной сессии. Если ему нужна другая роль, он завершает ход и возвращает **заказ финальным текстом**, а не выполняет чужую работу.

Форма заказа:

```text
ЗАКАЗ: u-<роль>
ЗАЧЕМ: какая неопределённость или работа блокирует результат
ЗАДАНИЕ: самостоятельный текст без «см. выше»
ЧТО ВЕРНУТЬ: координаты / дифф / числа / вердикт / изменённые файлы
ЦЕНА: бесплатно | деньги и оценка | живая БД | внешняя отправка
ЕСЛИ ОТКАЖУТ: допустимый запасной ход и ограничение результата
```

Главный агент проверяет зону обеих сторон, разрешения и стоимость. Отказ и его причина возвращаются заказчику и фиксируются в отчёте. Повторный одинаковый заказ без новых данных не обходит отказ.

## 22. Git, ветки модулей и обязательные коммиты
Работа ведётся в локальном Git; основная линия — `main`. Фактическое состояние репозитория перед первой операцией проверяется, а не предполагается по старому описанию. Remote не требуется. **Push не нужен и не выполняется.**
* Каждый прикладной модуль получает одну ветку `module/<имя>` для его backend, frontend и тестов. Первый модуль — `module/utility-rating`.
* Общая основа и регламент коммитятся в `main`; реализация модуля — только в его ветку.
* Принятая работа обязана быть закоммичена. Отчёт называет коммиты и отдельно перечисляет всё намеренно незакоммиченное; нельзя выдавать рабочее дерево за сохранённую историю.
* Для дефекта и критичного скоринга прибор с доказанным красным коммитится отдельно до реализации. Изменение измерения и предмета не смешиваются. Промежуточный красный коммит прибора не является разрешением сдать итоговую ветку красной.
* Общая конфигурация, независимые модули, массовое форматирование, регламент и посторонний рефакторинг разделяются на осмысленные коммиты.
* Чужие незакоммиченные изменения сохраняются. Не использовать reset, clean, force-push, rebase, переписывание истории или удаление ветки без отдельного разрешения владельца.
* Две пишущие сессии не работают в одной копии: каждая получает свою ветку и рабочую копию. Слияние в общую линию выполняет главная сессия после ревью.
* Секреты, `.env`, `.venv`, `node_modules`, `.artifacts`, реальные JSON-выгрузки и промежуточные данные в `dataset/`, содержимое `output/`, живые дампы и кэши не коммитятся; схемы и документация dataset из раздела 8 остаются отслеживаемыми.
* Удаление данных, живых томов и необратимые Git-операции подтверждаются отдельно. Разрешение на обычный коммит не включает их.

## 23. Фактические команды после flatten
Это минимальный командный контракт после появления соответствующих файлов. До scaffolding нельзя называть его запущенным. Все Python-команды выполняются из корня репозитория; активировать окружение не обязательно.

```powershell
py -3.13 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.venv\Scripts\python.exe -m pytest
.venv\Scripts\python.exe -m ruff check api contract core dossier sources utility_rating tests map-preparation
.venv\Scripts\python.exe -m uvicorn api.main:app --port 8000
```

Перед использованием проверяется наличие окружения, корневых requirements и перечисленных пакетов. Команда Ruff не сокращается ради пропуска проблемной зоны; если пакета ещё нет, scaffolding либо команда исправляются согласованно, а ложный успех не заявляется.

`README.md` содержит фактические подробности окружения и запуска. Если команда меняется, сначала в том же пакете обновляется README и затем согласуется этот командный контракт; заведомо неверные инструкции не остаются ни в одном месте.

**Frontend-команды не выдумываются заранее.** Только после появления фактического `frontend/package.json` исполнитель читает его `scripts`, lockfile и конфигурацию, запускает именно объявленные проверки и записывает команды в `README.md`. До этого список `npm test`, `npm run test` или иной предполагаемой команды действующим контрактом не является.

## 24. Приёмка владельцем и следующий шаг
Перед сдачей главный агент сверяет применимые к конкретному пакету пункты. Пункт про internal HTTP scoring относится **только к приёмке Compose**: он не применяется задним числом к текущему utility-rating и не означает, что сервис уже существует. Для самого Compose это требование не смягчается — без внутреннего scoring и перевода обоих прямых вызовов на адаптер пакет не принимается.

Чек-лист с явной областью применимости:
* механизм соответствует заданию, а не только названному примеру;
* скоринг имеет независимый численный эталон и обязательные граничные проверки;
* красный исходного прибора воспроизведён, итоговые запуски действительно зелёные;
* все потребители учтены, второй путь формулы и мёртвый код не добавлены;
* логи и артефакты собраны, секреты и живые дампы отсутствуют;
* Before/After понятен человеку, команды и вывод не придуманы;
* ограничения legacy dataset и пилотной выборки видимы;
* память и решения не объявлены существующими до их отдельного пакета введения;
* ветка и коммиты соответствуют модулю, чужие правки сохранены, удалённая отправка не делалась;
* runtime не использует внешний интернет, online tiles или online геосервисы;
* **Только при сдаче Compose:** scoring вызывается через внутренний HTTP и не доступен ни браузеру, ни хосту напрямую; существующие прямые вызовы `dossier/service.py` и `sources/legacy_dataset.py` переведены на адаптер `sources`.

Финальный ответ называет, что изменилось, какие команды фактически выполнены и что они вывели, что не проверялось, какие допущения и риски остались, какие коммиты созданы и какой следующий шаг имеет наибольшую ценность. Непроверенное остаётся непроверенным независимо от уверенности автора.

## 25. Offline/Compose — отдельное решение владельца
Этот раздел фиксирует решение владельца и уточняет предыдущие разделы в части контейнеров, сети и эксплуатации. **Docker + Docker Compose — отдельный пакет после обязательного logging-пакета.** Он выполняется в отдельной ветке `module/compose`, с собственными прибором, реализацией, ревью, коммитами, проверками и run-артефактами. До фактического появления Compose-файла его существование не заявляется. Internal HTTP scoring и `api.scoring_main` сейчас отсутствуют; их введение и перевод существующих прямых вызовов на `sources` — обязательная часть именно этого пакета, а не описание текущего дерева.

### Три обязательных сервиса
Целевой базовый Compose должен содержать ровно три функционально выделенных сервиса приложения:

| Сервис | Ответственность и граница |
|---|---|
| `api` | FastAPI, владение dataset и cache, сценарий досье; вызывает scoring только адаптером `sources` |
| `scoring` | отдельный stateless internal HTTP-расчёт с операциями `parse_dataset` и `score_city`; вся формула только в `utility_rating` |
| `frontend` | SPA под Nginx, Leaflet, локальный `L.imageOverlay`, markers, assets и локальный поиск по каталогу |

`scoring` — целевое имя контейнерного сервиса, а не разрешение завести новый корневой Python-пакет. В Compose внутренняя HTTP-дверь `api.scoring_main` должна использовать чистый `utility_rating`; публичный `api.main` и `dossier` не будут импортировать формулу. `sources` обязан предоставить client adapter к scoring, скрывающий HTTP, таймауты, коды отказа и проверку ответа. Второго расчёта в `api`, `dossier`, `sources` или frontend не допускается.

`api` владеет чтением dataset и cache и передаёт scoring только явно версионированный snapshot или данные по внутреннему контракту; scoring stateless и не ходит в базу. `parse_dataset` проверяет и нормализует набор, отличая структурный отказ и неполноту от корректного отсутствия событий. `score_city` получает только полный пилотный набор и не превращает неполные данные в нулевое среднее.

### Сеть и запрет внешнего runtime
Наружу на хост публикуется **только `frontend`**. `api` и `scoring` не публикуют host ports; `scoring` доступен исключительно внутри Docker network и только как внутренний HTTP-сервис. Браузер и frontend Nginx не проксируют к нему прямой доступ. Браузер обращается только к frontend, frontend — к `api`, `api` через `sources` — к `scoring`.

Ни один сервис во время runtime не ходит во внешний интернет. Внешние online tiles, Nominatim, Photon, Valhalla и другие online геосервисы запрещены без fallback. Self-host на своей машине разрешён последующим отдельным решением при реальной потребности, но не должен быть overkill.

Сейчас **не добавляются** PostgreSQL, Valhalla, Nominatim, Photon, central log server и map-tiles. Отдельный map-tiles сервис допустим только позже, если slippy map действительно заменит `L.imageOverlay`; для текущих 20 домов он не нужен. Изображение карты Приморского края — локальный asset frontend, подготовленный заранее отдельным этапом, а не скачиваемый при запуске.

Build-зависимости фиксируются корневыми requirements/constraints при их введении, frontend lockfile и точными версиями или digest базовых образов. Плавающий `latest` запрещён. Сборка использует фиксированные зависимости; готовые контейнеры после запуска не скачивают карту, пакеты, модели или геоданные из внешнего интернета.

### Health, readiness и смена dataset
У каждого сервиса есть собственный healthcheck и раздельные health/readiness:
* health означает, что процесс жив и способен выполнять внутреннюю проверку;
* readiness означает, что сервис готов принимать трафик: обязательная конфигурация и локальные assets доступны, dataset у `api` валиден, а необходимая внутренняя зависимость отвечает;
* неготовность не маскируется успешным liveness, а недоступность scoring не превращается в нулевой рейтинг.

Для `api` и `scoring` предусматриваются HTTP health/readiness; для `frontend` — проверки Nginx, SPA и локального изображения карты. Точные маршруты и команды фиксируются реализацией пакета в README, а не выдумываются до файла.

После смены dataset выполняется управляемый graceful restart затронутых сервисов: новые запросы ограничиваются на время drain, текущие завершаются в установленный срок, cache не смешивает версии наборов, старый процесс останавливается gracefully. Readiness возвращается только после повторного `parse_dataset`, проверки полного пилотного набора и успешного пробного `score_city`. Ошибка нового набора оставляет явное неготовое состояние; молчаливая подмена старым или частичным результатом запрещена.

### Отдельные журналы без центрального log-сервиса
`core/logging.py` вводится отдельным logging-пакетом до Compose; его наличие до этого не утверждается. В целевом Compose каждый сервис пишет собственный `execution.log` в **отдельный named volume**. Центральный сервер логов не создаётся. Централизация в `core/logging.py` означает единый код настройки Python, а не единое хранилище: каждая функционально выделенная часть логируется отдельно.
* `api` и `scoring` используют file handler из `core/logging.py` и общий маркированный формат из раздела 14; handlers не создаются в обход фабрики.
* `frontend` пишет Nginx `execution.log` файлом в своём volume с согласованными полями времени, уровня, сервиса, маркера, сообщения и безопасных metadata; browser console не заменяет этот файл.
* В каждом журнале применяются service marker и одинаковые правила секретов. Volume одного сервиса не становится скрытым журналом другого.
* Консольный `docker compose logs` — вспомогательный вывод, не замена файловым `execution.log`. Run-пакет связывает три файла с одним каталогом `.artifacts/runs/...`, сохраняет `env_snapshot` без секретов, `test_results.log` и `REPORT.md`.

### Командный контракт Compose после logging-пакета
Следующие команды — **цель отдельного Compose-пакета после logging-пакета**, а не утверждение, что файл уже существует или эти команды сейчас успешно запускались. Фактические имена файла, profiles и дополнительные options фиксируются в README реализацией; базовые имена сервисов менять нельзя.

```powershell
docker compose config
docker compose build
docker compose up -d
docker compose ps
docker compose logs --no-color api scoring frontend
docker compose restart api scoring frontend
docker compose down
```

`restart` использует настроенный grace period и сопровождается проверкой health/readiness, а не считается доказательством готовности сам по себе. `down` выполняется без удаления volumes; удаление volumes и данных остаётся отдельной необратимой операцией с разрешением владельца.

Приёмка пакета включает проверку конфигурации, повторяемой сборки, запуска и всех health/readiness, smoke сценария frontend → api → scoring, локального imageOverlay и поиска, отсутствия host ports у `api`/`scoring`, отсутствия внешних runtime-запросов при отключённом внешнем интернете, graceful restart после смены dataset и трёх независимых файловых журналов. Результаты сохраняются в артефактах прогона; незапущенные проверки не называются пройденными.
